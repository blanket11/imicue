# 実装計画と受け入れテスト

状態: M0〜M2のローカル版を実装。M3〜M5は未実装。実際の検証結果と未実施項目は [実装メモ](09-local-implementation.md) を参照する。

## 1. 進め方

小さな動作確認可能な単位で実装する。最初はM0〜M2で止め、APIキーがなくてもローカルで試せるものを作る。そこで挙動を確認してから外部API・静的配布へ進む。

| フェーズ | 作るもの | 完了条件 |
| --- | --- | --- |
| M0 基盤 | workspaces、TypeScript、検証/テスト基盤、.gitignore | クリーンな環境で依存解決・型検査・実テストが動く |
| M1 Core | 辞書検証、スナップショット、期間限定集計、Rules、共通ポリシー | 合成データで同じ判定を再現でき、見送りと境界テストが通る |
| M2 Browser | 属性計測、手動track、同意・保存・購読、Vanillaデモ | ブラウザで計測→辞書→Rules→結果が確認できる。外部AI通信なし |
| M3 Server/Jev | 固定契約のHTTP処理、入力制限、辞書解決、Jev Adapter | モックで異常系を含む統合試験が通る。実API確認は別ゲート |
| M4 配布/SSG | ESM/types/IIFE、Next.js static exportデモ | npm未公開のローカル成果物で双方が動き、キーを含まない |
| M5 公開準備 | 利用手順、制約、評価、貢献ガイド、リリース候補確認 | 未検証事項を明記し、公開操作前にオーナーの確認を受ける |

Jevキーがない場合でもM0〜M2とM4は進められる。M3のモックが通ったことと、Jev実APIで確認できたことは別々に報告する。

## 2. M0の詳細

既存ファイル、LICENSE、作業ツリー、AGENTS.mdの有無を読んでから始める。実装に先立ち現在の依存ライブラリの公式資料を確認し、サポート中のNode.jsとpackage managerのバージョンを固定する。

npm workspacesはcore/browser/serverの3責務を起点にし、まだ不要な空パッケージを大量に作らない。lockfileは1つ。パッケージ公開フラグはprivate=trueのままにする。

実際に実行可能なtypecheck、lint、unit test、buildを用意する。E2EはM2から追加する。空のテストや常に成功するダミーscriptで通過したことにしない。

.gitignoreで.env類、node_modules、ビルド成果物、テスト出力を管理から外す。`.env.example`はダミー値のみ許可する。既存Apache-2.0 LICENSEは変更しない。

GitHub Actionsを実装タスクで追加する場合は通常のread権限の検証だけとし、有料API、publish、deployment、pull_request_targetで外部PRコードを秘密付き実行する処理を含めない。利用者の手元で再現するコマンドを先に用意する。

## 3. M1の詳細

[データ契約](02-data-contracts.md) に従い、辞書を検証し、未登録参照や不正URLを拒否する。集計器へ時計を注入できるようにし、30分ウィンドウと容量超過をテストする。

[Rulesの式と共通ゲート](04-decision-engines.md) をそのまま基準実装にする。理由なく重みを変更したりAIへ置き換えたりしない。インターフェース設計上の変更が必要な場合はテストと仕様を同じ変更に含める。

日時・辞書の結合・製品判定・候補の除外はモデル非依存で実装する。UIやHTTPがなくても、固定snapshotからDecisionを得られる状態にする。

## 4. M2の詳細

初期デモは架空製品DemoContractの静的な数ページ。機能・料金・事例のシグナルと3つ程度の案内候補を用意する。Next.jsを先に導入せず、VanillaでCoreの独立性を確認する。

デモの確認パネルには、計測開始/停止/同意撤回/リセット、登録済みシグナルの説明、現在の集計、Rulesの採点、見送り理由を表示する。デバッグはローカル表示のみで、どこにも自動送信しない。

結果UIは小さな案内カードでよい。位置やブランドデザインには時間をかけず、閉じる操作・抑制・キー入力を妨げないことを確認する。UIはexampleに置き、Coreに含めない。

同意の操作例はライブラリを試すためのものと明示し、あらゆるサイトの法的同意要件を満たす完成済みバナーとは扱わない。

## 5. M3の詳細と実APIゲート

Nodeのlocalhostサンプルとモックproviderを先に作る。受信制限、同意撤回中の応答破棄、期限切れ辞書、429、timeout、不正応答を再現する。

公式SDKの呼び出しは現行の型を確認して実装する。実API試験は、オーナーがローカルにキーを設定し、明示的に試験を許可した時だけ実行する。キーをチャットや仕様書への貼り付けで受け取らない。

実API試験では合成データのみ使い、初回は最大5リクエストに制限する。`RUN_JEV_INTEGRATION=1`等の明示フラグで通常テストと分ける。キーなしではskip理由を報告し、合格と数えない。大量評価や価格比較は別途許可を受ける。

## 6. M4の詳細

ESMと型定義を生成し、IIFEは `window.Imicue` に最小APIを公開する。script読み込みだけで自動計測を開始しない。グローバル名競合と二重initを処理する。

CDN相当の検証はローカル静的サーバーから固定ファイルを読み込む形で行う。存在しないnpm/CDN URLをREADMEに完成した導入先として掲載しない。

Next.jsデモは `output: 'export'` でビルドし、生成されたoutを静的サーバーで開いて検証する。`next dev`が動くだけでは完了にしない。Client側で開始/cleanupとpageIdの遷移をつなぎ、SSR時にDOMへ触れない。

ルールモードは完全静的に動く。リモートモードは別のNode endpointを指定して動かす。exportアプリに動的POST Route Handlerを埋め込まない。

## 8. 軽量性の検証

Browser+Core+Rulesの配布サイズはgzip 25KiB以内を初期目標とする。Jev SDK、React、UIライブラリをここに含めない。未達時はサイズ内訳を報告し、機能削除や目標緩和を黙って行わない。このサイズは未計測の目標値である。

200要素のデモで、毎フレーム全DOM走査、永続的な高速polling、scrollごとのAPI呼び出しがないことを確認する。計測条件・ブラウザ・端末を記録して負荷を測る。「軽い」とだけ書かない。

## 9. 意味的な評価セット

初期に最低12件の合成シナリオを作る。初訪問、機能中心、料金中心、事例中心、複数の関心、興味の変化、別製品混在、単発の長時間放置、推薦由来のみ、期限切れ候補、既読候補、すべて弱い入力を含める。

許容contentId集合またはabstainを人がレビューする。開発用とholdoutを分離し、同じfixtures・候補集合でRules/ラベル中心Jev/辞書付きJevを比較する。件数が少ない段階では精度の一般化や統計的優位を主張しない。

実APIなしのモック評価は接続契約の検証であり、推薦品質の比較には使えない。A/BテストやCV改善の検証基盤をこの段階で追加しない。

## 10. 各作業の完了報告

変更ファイル、実装した仕様、実行コマンドと結果、未実施の試験と理由、残る設計判断、次の最小作業を報告する。未実装・未実行・失敗・合格を分ける。

実装していないscriptの成功、存在しないデプロイURL、npm公開済み、実API確認済みといった報告はしない。Issue/Project更新や公開は別指示があった時だけ行う。
