# テストと受け入れ条件

この文書はImicueへ変更を加える開発者向けの検証手順。まず動かしたい場合は[ローカルデモ](guides/local-demos.md)を参照する。過去に実行した件数や実測値は[検証記録](README.md)に分け、ここでは現行コードで再現するコマンドと守るべき条件を示す。

## 1. 通常の検証を実行する

Node.js 24.14.0 / npm 11.9.0を使い、リポジトリ直下で実行する。

```sh
npm ci
npx playwright install chromium firefox webkit
npm run check
```

`check` は型検査、lint、単体・統合試験、全ビルド、配布・梱包検査、Rulesの回帰評価、ブラウザ試験を実行する。Jevの実API、npm公開、デプロイは実行しない。失敗した項目や実行できなかったブラウザを、成功したものと分けて記録する。

変更範囲を確認するときは次のコマンドを使える。ブラウザ試験では必要な配布物を先にビルドする。

| 変更対象 | 主なコマンド |
| --- | --- |
| 型・実装全般 | `npm run typecheck`、`npm run lint`、`npm test` |
| 辞書・集計・Rules | `npm test`、`npm run eval:rules` |
| Browser・Vanilla・Next.js・配布物 | `npm run build`、`npm run test:e2e` |
| バンドルとパッケージ | `npm run build`、`npm run check:bundle`、`npm run check:distribution`、`npm run check:package` |
| 紹介サイト | `npm run build:site`、`npm run check:site`、`npm run test:site` |

## 2. 変更箇所に応じて検証する

Coreの辞書参照、日時比較、製品判定、候補除外はモデル非依存で扱う。時計を固定したSnapshotから同じDecisionを再現し、境界値と見送り条件をテストする。APIや採点方針を変更するときは、[データ契約](02-data-contracts.md)と[判定仕様](04-decision-engines.md)も更新する。

Browserでは計測の許可、開始・停止、同意撤回、ページ移動、保存の復元、古い応答の破棄を確認する。単体テストのObserverだけで対応を判断せず、実ブラウザで可視性・intersection・静的配信を確認する。デモの同意操作は利用例であり、各サイトの同意要件を満たす完成済みバナーではない。

Serverでは入力・容量・利用制限、期限切れ辞書、429、timeout、不正応答をモックで再現する。Jevの複数要求を扱う変更では、全結果が揃う前に推薦を返さないこと、未送信分だけ利用枠を返すことも確認する。

配布物は生成済みのESM・型定義・IIFEを使い、ソースを参照しない利用環境を検査する。Next.jsは `output: 'export'` の生成物を静的サーバーから配信して確認する。React Strict Modeのeffect再実行は別の統合試験で扱う。scriptの読み込みだけでは計測を開始せず、ブラウザ成果物へサーバーSDKや秘密値を含めない。

## 3. 実APIの試験を分ける

Jevの実API試験には課金が発生し得る。通常の検証コマンドとは分け、ローカルのキーと `RUN_JEV_INTEGRATION=1` などの実行フラグを明示する。手順は[サーバーとJevの接続](guides/server-and-jev.md)を参照する。

合成データを使い、試行数・同時数・費用上限を実行前に決める。疎通用の `test:jev` は既定1回、最大5回。キーやフラグがないときのSKIPを合格に含めない。大量評価は疎通とは別に予算を決め、入力本文・認証情報・生のエラー本文を公開ログへ残さない。

モックは通信契約を確認するもので、実モデルの品質や料金を測るものではない。反対に実APIの成功だけで、異常系や共有利用制限の検証を省略しない。

## 4. 受け入れ条件

| ID | 試験 | 期待結果 |
| --- | --- | --- |
| C01 | 未知signal/topic/content、危険キー、不正href | 初期化またはHTTP検証で拒否。AI呼び出し0 |
| C02 | 古いdefinitionVersionと新しいserver | 409/definition_mismatch。最新辞書で推測しない |
| C03 | 30分を超えたイベント・境界をまたぐ表示区間 | 範囲内の期間だけを集計する |
| C04 | 同じ入力、時計、policyVersionでRulesを再実行 | 同じ値・同じ推薦/見送りになる |
| B01 | 1秒表示、連続3秒表示、連続20秒表示 | viewsは順に0、1、1。時間と回数が別に記録される |
| B02 | 1秒未満の出入りと1秒以上の離脱 | 前者は同episode、後者は新episode。qualified前の連続時間はリセット |
| B03 | 高さ3,000pxのsectionと800px viewport | 全要素50%を条件にした取りこぼしが起きない |
| B04 | タブ非表示、無操作60秒超、復帰、端末停止相当の時計差 | 非活動中を表示時間に加算しない |
| B05 | 同一IDの重複表示、親子属性、連打 | 時間の二重加算、親子クリック重複、回数水増しを抑える |
| B06 | Mutation追加/削除、React二重mount、destroy | 監視対象が更新され、残存listener/timerがない |
| B07 | 同意前に保存済みデータが存在 | 同意前はstorageを読まない・観測しない・通信しない |
| B08 | 同意撤回中にAPI応答、ページ変更中にAPI応答 | 応答を破棄。データもUIも復活しない |
| B09 | storage不可・壊れたJSON・未来時刻・旧バージョン | 安全にmemoryへ退避または破棄。他のstorageを削除しない |
| B10 | 1,000件超の内部記録、200要素超 | 容量を制限して診断し、欠落を隠して推薦しない |
| D01 | 初見/弱い入力、候補なし、同点 | 見送りが正常なDecisionとして返る |
| D02 | 現在の内容、無効/期限切れ、他製品、dismissed/completed | 該当候補は推薦されない |
| D03 | recommendation由来の行動だけを増やす | directの関心として自己増幅しない |
| D04 | RulesとJevのscore/confidence | 値の意味を分け、Rulesに架空のconfidenceを作らない |
| D05 | 候補外ID、NaN、範囲外、欠けたモデル応答 | invalid_result。危険な値をそのままUIへ渡さない |
| D06 | 有効候補9・21・100、末尾に関連候補、候補順を逆転 | 全件評価し、件数・登録位置だけで選択不能にならない |
| D07 | 同じ100候補、機能中心と事例中心の閲覧、クリック0 | 最低観測量を満たせば各記録に合う案内を評価する |
| D08 | Jev分割の欠落・不正・部分失敗・全体期限 | 未評価候補を隠さず全体を見送る。全件検証前には推薦しない |
| S01 | 巨大body、負の値、不正配列、任意prompt/baseURL | HTTP境界で拒否し、プロバイダーを呼ばない |
| S02 | 429/5xx/timeout/資格情報なし | 隠れた自動retry・別有料モデルへの切り替えをしない |
| S03 | 同時要求と全体予算超過 | 上限前に原子的に枠を確保。超過時のprovider呼び出し0 |
| S04 | ビルド済みブラウザ成果物を検査 | Jev SDK、serverモジュール、実キー、秘密値が含まれない |
| S05 | 複数分割と同時判定、途中の中断 | 全試行数を先に予約し、外部呼び出しごとの並列枠を守る。未送信分のみ返却 |
| S06 | 100件の応答と最大ID長、32KiB境界 | 全候補の応答を検証し、32KiB超を拒否する |
| P01 | Next.js export後の配信とクライアント遷移 | 動作し、DOM参照エラーやlistener重複がない |
| P02 | ESMとIIFEを別ページで使用 | 同じ契約で結果が得られ、scriptだけでは計測開始しない |
| P03 | ローカルRulesデモを使用 | 判定用の外部通信0、キー不要 |

単体テストでは時計・transport・providerを注入する。ブラウザの可視性・intersection・静的配信は実ブラウザでも確認する。mockだけでブラウザ対応を主張しない。

## 5. サイズと計測負荷

Browser+Core+Rulesの配布サイズはgzip 25KiB以内を初期目標とする。Jev SDK、React、UIライブラリをここに含めない。未達時はサイズ内訳を報告し、機能削除や目標緩和を黙って行わない。ビルドしたファイルを `npm run check:bundle` で測定する。過去の測定値は[100候補の評価記録](21-candidate-scale.md)を参照する。

200要素のデモで、毎フレーム全DOM走査、永続的な高速polling、scrollごとのAPI呼び出しがないことを確認する。計測条件・ブラウザ・端末を記録して負荷を測る。「軽い」とだけ書かない。

## 6. 推薦内容の評価

基本の回帰試験には12件の合成シナリオを使う。初訪問、機能中心、料金中心、事例中心、複数の関心、興味の変化、別製品混在、単発の長時間放置、推薦由来のみ、期限切れ候補、既読候補、すべて弱い入力を含める。

許容contentId集合またはabstainを人がレビューする。開発用とholdoutを分離し、同じfixtures・候補集合でRules/ラベル中心Jev/辞書付きJevを比較する。件数が少ない段階では精度の一般化や統計的優位を主張しない。

実APIなしのモック評価は接続契約の検証であり、推薦品質の比較には使えない。A/BテストやCV改善の検証基盤をこの段階で追加しない。

100候補の拡張では、調整用と未使用の評価用をテーマごとに分ける。全件ScoreとChoice併用を比較し、分割数・token数・費用・判定時間・全件完了率と、許容候補への一致を別に記録する。AIが作った許容案を人のレビュー済み正解と呼ばない。候補順や分割の影響、長文条件、実ブラウザで受け取れた有効な結果も確認する。手順と結果は [100候補の評価記録](21-candidate-scale.md) を参照する。

## 7. 変更と検証結果の報告

変更ファイル、実装した仕様、実行コマンドと結果、未実施の試験と理由、残る設計判断、次の最小作業を報告する。未実装・未実行・失敗・合格を分ける。

実装していないscriptの成功、存在しないデプロイURL、npm公開済み、実API確認済みといった報告はしない。外部への公開やIssueの更新は、依頼された範囲に含まれていることを確認して行う。
