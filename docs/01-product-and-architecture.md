# Imicue v0.1 — 目的・スコープ・アーキテクチャ

仕様状態: Draft / 実装前。作成日: 2026-09-26。

本書の「必須」はv0.1の受け入れ条件、「初期値」は検証前の設計判断を表す。実装済みのAPIや、推薦精度・CV改善を保証するものではない。

## 1. プロダクトの目的

Imicueは、WebサイトやWebアプリの行動シグナルに意味を付け、ルールまたはAIによる判断につなげる、UIを持たないオープンソースライブラリである。

利用者がHTMLに登録済みのシグナルIDを付ける。ブラウザがその要素の表示や操作を集計する。辞書が「そのIDは何についての内容か」を説明する。判定エンジンが構造化した結果を返し、利用サイトが結果の使い方を決める。

```text
HTMLの data-imicue-signal / 手動 track()
        ↓
Browser: 同意・観測・期間限定の集計
        ↓
Core: 観測事実と定義を結合した判定入力
        ↓
Rules（ブラウザ内） または Server → Jev
        ↓
候補ごとの評価 / 推薦するcontentId / 見送り
        ↓
利用サイトのUIや処理
```

Jevは最初の外部AIアダプターであり、Imicue本体の必須依存にはしない。

## 2. 想定する利用場面

主対象は、製品・サービスの紹介サイト、イベントの案内サイトなど。機能の説明を見ている訪問者に機能ガイド、事例を調べている訪問者に関連事例などを案内する。資料請求だけに固定しない。

Webアプリでも、登録済みの「機能を開いた」「操作を完了した」などを `track()` から入力できる。予定の本文、検索語、ユーザー属性を収集する仕組みは作らない。

公開デモには架空の製品 `DemoContract` を用いる。勤務先・個人の既存サービスのソースコード、内部設定、実ユーザーの履歴は持ち込まない。

## 3. 設計原則

| 原則 | 実装への要求 |
| --- | --- |
| 観測と推定を分ける | `pricing`は内容の分類。`considering_purchase`を閲覧済み事実として加算しない |
| 意味は辞書で定義する | HTMLにはID。説明・製品・トピックはバージョン付き設定に置く |
| 辞書の結合はコードで行う | Jevに巨大な辞書を渡してIDを探させない |
| UIと判定を分ける | コアにポップアップ、CSS、DOM書き換えを含めない |
| 見送りを正常な結果にする | 入力不足、候補なし、低い関連性、曖昧な同点では出さない |
| APIキーなしでも試せる | ルール判定とVanillaデモは完全にローカルで動く |
| 収集は明示的に開始する | 初期状態では観測・保存・判定用通信をしない |
| 精度は比較する | 辞書付きJevがルールやラベルだけの入力より良いかを評価する |

## 4. v0.1に含めるもの

HTML属性からの観測、登録済みアクションの手動記録、辞書検証、期間を限定した集計、任意のsessionStorage保存、スナップショット購読、ルール判定、任意のJevサーバー接続、構造化した判定結果の購読を実装する。

配布用ビルドはES ModulesとTypeScript型定義、および通常のscriptタグで読み込めるIIFE形式を用意する。CDN対応とはこの静的JSを配布できることを指す。npm公開・実在するCDN URL・独自ドメインは別の公開作業であり、自動では実施しない。

Vanilla JSデモとNext.jsの `output: 'export'` デモを作り、同じコアで動くことを確認する。Next.js用の専用SDKは作らず、初期化・破棄・ページ遷移を接続する小さな利用例で示す。

最初の組み込み判断は「登録したコンテンツ候補の関連性を評価すること」に絞る。関心分類を必ず先に行う二段階AIパイプラインにはしない。利用者は観測スナップショットを購読して独自処理にも使える。

## 5. v0.1に含めないもの

SaaSの管理画面、アカウント、課金、複数顧客のホスティング、WordPressプラグイン、React/Vue専用パッケージ、汎用ノーコードルール編集、長期ユーザープロファイル、クロスサイト追跡、CRM連携、A/Bテスト基盤、ベクトルDB、自由文生成、任意スキーマのAIワークフローは対象外とする。

購入意思、職種、個人の属性を断定する機能を作らない。認証、権限、価格決定、課金の根拠としてこの判定を利用しない。

UIデモは必要だが、ポップアップの完成品をライブラリ本体に取り込まない。

## 6. 論理構成と依存方向

```text
packages/core
  設定・入出力の型 / 検証 / 集計 / ルール判定 / 共通ポリシー
  DOM、React、Node専用API、Jev SDKに依存しない

packages/browser → core
  DOM計測 / lifecycle / storage / scheduler / HTTP transport
  Jev SDK・秘密キーに依存しない

packages/server → core
  authoritativeな辞書 / 入力検証 / 制限 / Jevアダプター
  ブラウザのDOMに依存しない

examples/vanilla
examples/next-static
examples/server-node
```

この3責務を基本とする。過剰な分割を避けるため、Jevアダプターは当初server内の独立モジュールでよい。パッケージ名 `@imicue/*` は設計上の仮称であり、npmスコープ取得済みとは扱わない。

初期実装ではTypeScript strict、npm workspaces、単一lockfileを推奨する。実行環境はNode.js 24系を初期候補とし、導入時に公式のサポート状況と依存パッケージの対応を再確認して固定する。テストはVitestとPlaywright、ビルドはtscと必要最小限のバンドラーを使う方針とする。これらはImicueの設計選択であり、APIの互換性に関わる変更は記録する。

## 7. 静的サイトとサーバーの境界

ルールモードは静的サイトだけで動作する。Jevモードだけが別のサーバーまたは関数エンドポイントを必要とする。

```text
静的HTML + browser bundle
        │ 登録済みIDと数値の集計だけを送信
        ↓
利用者が管理する判定サーバー
  辞書の解決 / ポリシー / APIキー
        ↓
Jev
```

Next.jsの静的エクスポートでは動的POST APIを提供できない。またClient Componentも事前レンダリングされるため、import時にwindow/documentへ触れない。[Next.js公式資料](08-references-and-decisions.md#s6)

Cloudflare Workers等のEdge対応は未検証。Nodeで動くことを根拠に、すべてのホスティング環境へ対応済みとは記載しない。

## 8. 将来の拡張余地

判定エンジンの置換、CMS向け属性設定支援、WordPressプラグイン、管理サービスは、現在のBrowser/Core/Server境界の外側に追加する。v0.1のために汎用プラグイン市場やマルチテナント基盤を先行実装しない。

外部からの参加は通常のIssue・Pull requestで受ける。既存のApache-2.0 LICENSEは維持する。本仕様を実装するタスクだけでは、リポジトリ権限、ライセンス、GitHub Project、npm公開設定は変更しない。

## 9. 成功と呼べる状態

架空の静的サイトに数個の属性を付け、明示的に計測を開始すると、表示の記録・辞書の意味・判定結果を確認できる。APIキーがなくても試せる。Jevモードはサーバー内のキーでのみ動作する。見送り・通信失敗・同意撤回でもサイトの本来の利用を壊さない。

この状態は「技術的なPoCの成立」であって、推薦精度やリード獲得の改善が実証された状態ではない。品質検証とリリース判定は [実装計画・受け入れテスト](06-implementation-and-tests.md) に従う。
