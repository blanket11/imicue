# 100候補への拡張と評価

> 2026-09-27の実装・検証記録です。条件付きの実測であり、実サイトでの品質や全ブラウザでの動作を保証しません。現在の操作手順は[ローカルデモ](guides/local-demos.md)を参照してください。

この記録の集計値は、当時の合成データに対する測定です。デモの題材と評価fixtureは後から更新されています。掲載値を現在の読書ノート題材の品質評価として解釈しないでください。保存した結果ファイルの一部fixture IDは一般化してあり、記録内のfixtureHashは当時の入力値を示します。

確認日: 2026-09-27。対象は [Issue #4](https://github.com/blanket11/imicue/issues/4) で承認された、全件Scoreと容量による分割である。

**100件の案内先を登録し、クリックのない複数回の閲覧から全候補を評価できるようにした。** RulesとJevの共通処理にあった8候補制限を外し、Jevは全候補の回答がそろってから判定する。合成の未使用100ケースでは案内60件・見送り40件が期待案に一致した。ただし、期待案はAI作成で人の確認前であり、実サイトでの推薦品質を保証する結果ではない。

## 実装と維持した条件

| 対象 | 変更後 |
| --- | --- |
| 辞書 | contents最大100、pages最大200、定義JSON全体2MiB以下 |
| Core | Jev向けに意味を展開した入力は1MiB以下。件数だけによる8候補制限を撤去 |
| Jev | 共通stateは観測・辞書説明・最近の行動のみ。各Score質問に候補1件を置く |
| 分割 | contentId順に整列し、1要求64KiB以下へ分割。stateと1質問を含む要求は24KiB以下。最大8要求 |
| 呼び出し | 最大2並列、1要求2秒、全体3秒、自動再試行0 |
| 完全性 | 回答の全ID・件数・モデル・数値範囲を検証。一部の失敗・欠落・中断でも全体を見送り |
| 版 | schemaVersionは0.1を維持。Jev policyは `jev-rubric-v4`、adapterはv2 |

byte上限はUTF-8 JSONの資源制限で、モデルのtoken上限を保証するものではない。長い説明・多数の観測・topic展開によっては100候補未満でも送信前に `capacity_limit` となる。説明を黙って切り詰めたり、未評価候補を0点で埋めたりしない。

最低観測量は、有効なdirect観測のqualifiedViews合計2以上、またはclicks＋actions合計1以上のままとした。同じセクションの有効閲覧2回でも満たす。有効閲覧1回を長時間表示するだけで判定を開始する変更はない。

Jevの最終観測5分以内、記録・既読等の30分保持、製品・期限・完了・既読・閉じた案内の除外、score 0.65・confidence 0.60・候補差0.10の出力条件を維持した。同意撤回・ページ移動・revision更新後に古い応答を表示しない条件も変更していない。5分は厳密なローリング集計ではなく、最終観測時刻による選別である。

## 外部APIの枠を判定単位と分けた

判定受付のlimiterとは別に `ProviderUsageLimiter` を追加した。全分割の試行回数を先に予約し、各呼び出しで並列枠を取る。未送信分だけを返却し、失敗・タイムアウトも送信済みの試行として数える。中断後もローカル処理が終了するまで並列枠を保持する。提供元内部の処理停止や課金取消しは保証しない。

開発用メモリ実装は2並列・30回/分・100回/日。本番では判定受付とproviderの両方に共有limiterが必要で、開発用のままなら起動を拒否する。共有カウンターの実装は今回含めない。詳しい契約は [セキュリティ仕様](05-security-and-privacy.md#6-apiキーと課金乱用対策) を参照する。

## 採点基準の調整と方式比較

最初はv3の基準を分割方式へそのまま移した。調整用30ケースのうち、案内すべき18件中14件で案内し、4件を見送った。いずれも事例が1位だったが、同じ題材の機能ガイドも高得点となり、次点との差0.10を満たさなかった。

そこで段階2・3を、同じ題材かどうかに加え、辞書に書かれた「問い・操作・説明の観点」が対応するかで区別した。例えば機能の設定手順と組織の導入事例は、題材が同じでも説明する内容が異なる。訪問者の意図や購入意思を推測する条件は加えていない。改定後の調整用30件は、案内18/18、必要な見送り12/12となった。ここで基準を固定し、未使用データへ進んだ。

予備比較は**調整前の基準**で、同じ2テーマ・通常10ケースを使った。各候補をScoreで採点する方式と、101択Choice（100候補＋none）から上位3件をScoreで再評価する実験を比較した。

| 通常10ケース | 全件Score | Choice＋上位3件Score |
| --- | ---: | ---: |
| 推薦の期待案との一致 | 5/5 | 6/6 |
| 案内すべきケースでの案内 | 5/6 | 6/6 |
| 必要な見送り | 4/4 | 4/4 |
| API試行 | 30 | 18 |
| 判定時間 中央値 / p95 | 443 / 692 ms | 390 / 447 ms |
| 入力料金の推計 | $0.01506 | $0.00424 |

Choiceは費用が小さかった一方、全件Scoreで2位だった競合候補を上位3件から落としたケースがある。この結果、候補差が広がって案内が出た。単純に推薦が増えたことを品質改善とは解釈できない。上位3件への期待候補残存は6/6にとどまり、98%という目標を統計的に裏付ける件数でもない。

1000文字の説明を持つ100候補の予備試験では、全件Scoreは2/2件を各7要求で完了した。Choiceは2/2件とも64KiBを超えて送信前に拒否した。Choice方式は比較スクリプトだけに残し、本体のDecisionへ部分評価を混ぜていない。改定後の基準でChoiceを再測定する作業は未実施である。

## 未使用100ケースの結果

調整用6テーマと評価用20テーマを分けた。評価用は各テーマにつき、機能・事例・言い換え・無関係・曖昧の5条件、合計100ケースである。機能・事例・言い換え・無関係は同じ100候補を使い、観測だけを変える。曖昧条件では関連候補を2件同内容にする。候補IDの位置はテーマごとの固定seedで分散させた。

観測は概要1回・6秒、対象セクション1回・60秒、クリック・操作0。topicはなく、候補説明は短い日本語の合成文である。提案時の各200文字条件とは分け、後述の容量試験で200文字・1000文字を測る。評価用の初回実行は2026-09-27 10:57:49 UTCで、過去利用回数は0だった。

## デモとブラウザ

`/catalog/` は100件の個別ID・個別URLを持つVanilla例である。読書メモの検索と読書記録の整理を題材にし、`?topic=cases` では同じ辞書のまま閲覧内容を切り替える。標準はRulesで、APIキー不要。概要と詳細を順に表示し、詳細を30秒ほど表示すると関連する案内が出る。

計測開始・同意撤回・判定結果を確認できる。候補一覧やデバッグ操作は観測対象に含めない。遷移先100ページは共通の静的テンプレートを使った架空ガイドで、フォーム送信はない。このデモはmemory保存であり、ページ横断保存は既存のsessionデモで確認する。

Chromium・Firefox・WebKitで、100候補のRules、機能／事例の閲覧、モックHTTP、モバイル、撤回の15試験が成功した。ESM/IIFEの100候補の閲覧・撤回も6試験が成功した。

実APIのブラウザ試験は時計を進めず、2セクションを各3.1秒表示した。クリック・操作は0で、応答を受け取る前に観測対象外へ移動して表示時間の更新を終える。3ブラウザとも全件採点・結果採用・カード表示・意味一致・同意撤回に成功した。許可前・開始前のPOSTは0件で、ブラウザへのAPIキー・Server SDKの混入やページエラーは検出されなかった。

| ブラウザと閲覧 | 案内先 | POST本文 / Decision本文 | 完全応答 / 採用確認まで |
| --- | --- | ---: | ---: |
| Chromium・機能 | catalog-099 | 801 / 14,693 B | 794 / 798 ms |
| Firefox・事例 | catalog-098 | 786 / 14,656 B | 574 / 584 ms |
| WebKit・機能 | catalog-099 | 801 / 14,622 B | 655 / 659 ms |

採用確認時間はPOSTイベントから同じsnapshotIdのDOM表示を検出するまでで、Playwrightの通信・ポーリング遅延を含む。ブラウザの検証関数だけの処理時間ではない。各ブラウザ1回、合計3回の結果を本番の採用率と呼ばない。

Safari製品版26.4では、既存の閲覧試験で `document.visibilityState='hidden'` が続き、100候補の試験に到達しなかった。対象要素は画面範囲内で、最後の確認ではfocusもあった。原因をOSロックと断定せず、製品版Safariの今回の検証は未完として残す。非表示時の計測停止を無効化する変更はしていない。WebKitの成功とSafari製品版の成功は区別する。

ローカルの自動検証はtypecheck・lint、単体／統合304件、既存を含むE2E 105件、紹介サイトE2E 15件が成功した。新しいESM/IIFEの閲覧試験は最初の実行で表示時間不足により6件失敗し、判定時刻を33秒へ修正後、対象6件を全ブラウザで再実行して成功した。build、bundle上限、配布物の型・100候補の利用例、npm packのdry-run、サイト検査、Rulesの12ケース回帰も成功した。

## 移行と再実行

Core／Browser／Serverを一緒に更新する。旧ブラウザは新policyや100件の定義を受け付けない。段階的に更新する場合は旧エンドポイントを併存させる。辞書を変更するときはdefinitionVersionも更新し、古いsession記録を自動継承しない。

`buildJevRequest` は1要求に収まる場合の互換用関数として残した。複数要求が必要な入力には `buildJevRequests` を使う。本番handlerには共有provider limiterを指定した `createJevEngine` の戻り値をそのまま渡す。スプレッドで複製したengineは登録情報を失うため本番では拒否する。数値の利用量は `onUsage` で取得できる。

```sh
npm ci
npm run dev:fixtures
# http://127.0.0.1:5194/catalog/
# http://127.0.0.1:5194/catalog/?topic=cases

# APIを呼ばず分割数・容量を確認
npm run eval:catalog -- --suite pilot --plan
node --import tsx --conditions=imicue-source scripts/measure-catalog-capacity.ts --suite capacity --plan
```

実API評価はキーをサーバー環境に設定し、実行範囲と費用を承認したうえで個別に実行する。`.env.local`、生の評価結果、600回の累積台帳はGit対象外である。台帳を削除して同じ承認枠の残数を戻さない。

```sh
RUN_CATALOG_EVALUATION=1 node --env-file=.env.local --import tsx --conditions=imicue-source scripts/evaluate-catalog.ts --suite dev --live
RUN_CATALOG_EVALUATION=1 node --env-file=.env.local --import tsx --conditions=imicue-source scripts/evaluate-catalog.ts --suite holdout --live
RUN_CATALOG_BROWSER=1 node --env-file=.env.local --import tsx --conditions=imicue-source scripts/catalog-browser.ts
```

ブラウザ試験は先に `npm run dev:fixtures` で5194番の開発用画面を起動し、5193番を空けてから実行する。スクリプト自身がローカル判定サーバーを起動・終了する。1ブラウザ1判定・最大8試行、全体最大24試行を、共通の600試行台帳と併用する。通常のデモを実APIへ常時つないだまま繰り返す検証にはしていない。

### 結果ファイルと終了コードを読む

現在の評価スクリプトは、技術的に試験が完了したか、作成済みの期待案に一致したか、人が推薦品質を確認したかを分けて記録する。JSONでは、まず `status` と `completionStatus` を確認する。

| フィールド | 内容 |
| --- | --- |
| `status` | 実行中は `running`、完了は `completed`、失敗は `failed`、未実行は `skipped`、APIを呼ばない計画は `planned` |
| `completionStatus` | 技術的な完了状態。`running / completed / failed / incomplete / not_started` |
| `authoredExpectationStatus` | 作成済みの期待案との一致。`all_matched / mismatched / incomplete / not_evaluated` |
| `humanReviewStatus` | 人による推薦品質の確認。現在は `pending` で、一致しても品質合格へ変更しない |

比較評価（`eval:jev` / `eval:catalog`）の終了コード0は全件を技術的に完了したことを示し、期待案との不一致も終了0で `authoredExpectationStatus: 'mismatched'` に記録する。技術的な失敗や未完は終了1である。

100候補のブラウザ試験は、従来の受け入れ条件として期待候補との一致も必要である。技術的に全件完了しても誤った候補なら、`completionStatus: 'completed'`、`authoredExpectationStatus: 'mismatched'`、`humanReviewStatus: 'pending'`、全体の `status: 'failed'` と終了1を記録する。期待候補に一致しても、人による推薦品質の確認が済んだことにはならない。

実行フラグを指定しなかった場合はAPIを呼ばず、終了0で `status: 'skipped'` となる。実行フラグを指定したのにキーがなければ、終了1で `status: 'failed'`、`reason: 'api_key_missing'` となる。catalog評価の `--plan` または `--live` なしは、終了0の計画出力であり、実APIの成功に数えない。

catalog評価の最新結果は `test-results/catalog-evaluation.json`、ブラウザ試験は `test-results/catalog-browser.json` に保存する。Jevの接続・比較・ブラウザ試験も、それぞれ `jev-integration.json`、`jev-evaluation.json`、`jev-browser.json` を同じディレクトリに保存する。SKIPや起動失敗も最新ファイルを置き換えるため、前回の成功を今回の結果として読まない。実行ごとの記録は、時刻とUUIDを付けた別ファイルに残す。SKIPや起動失敗には測定値がない場合があり、`summary` や `results` だけで合否を判断しない。

### 費用台帳のロックが残った場合

異常終了でロックが残った場合は、先にcatalogの評価・ブラウザ試験・容量試験のプロセスをすべて停止する。復旧が完了するまで新しい試験を始めず、リポジトリのルートで次を実行する。APIキーや `.env.local` は不要である。

```sh
npm run recover:catalog-budget -- --confirm-no-running-tests
```

所有プロセスが稼働中のロックは回収しない。古いロックや所有情報が欠けたロックは、全試験を停止したことを確認したうえで、上のフラグを指定して回収する。復旧はロックだけを削除し、`test-results/catalog-budget.json` の累積試行と未確定の予約を保持する。台帳を削除・リセットして試行枠を戻さず、復旧コマンドが成功してから試験を再開する。

## 費用と残る確認

モデルは `jev-1.13.0`、SDKは0.6.0。2026-09-27確認の[公式単価](https://docs.typesafe.ai/models)は入力100万tokenあたり$0.042、出力無料で、usageの入力tokenから推計した。累積台帳は送信前に試行を計上し、usage不明時は保守的な予約額を残す。請求額そのものを保証する仕組みではない。

**今回の合計は596試行、7,328,759入力token、推計$0.30781。** 承認枠600試行・約$2以内で終了した。HTTPの非200・通信失敗は0件。予備比較のChoice長文2件は送信前容量拒否であり、通信成功や全候補評価成功に数えていない。追加の有料試験は行っていない。

公開用の[数値・ケース別結果](evaluations/2026-09-27-catalog.json)には、調整前後の実行日時・候補ID・上位スコア・容量・時間・費用を残した。キー、リクエスト本文、ヘッダー、個人の環境情報は含めない。未使用100ケースのfixtureHashは `c50d76cac882eae85a91919d824bd18b79dff6518ce7bed4117a28f4383d1293`、最終質問テンプレートのpromptHashは `4ac52343985ccb8cb1102b7f09c73ece77114c9ed9e0dadb6f0dde06d73cae96`。質問ハッシュの自動記録は評価後に追加したため、既存結果への最終ハッシュは変更していないテンプレートから追記した値である。調整前の結果には最終ハッシュを付けていない。

人によるラベル確認、実サイトの辞書・利用者を使った品質評価、実モバイル端末、長時間の運用・負荷、本番共有limiter、Edge環境は未検証または未実装である。フォーム入力の負担や案内先の優先度を表す新フィールドは追加していない。公開・npm配布・mainへのマージはこの作業では行わない。
