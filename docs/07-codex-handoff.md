# Codexへの引き継ぎ

このファイルは依頼文と作業上の制約をまとめたもの。まだ実装を開始・完了したことを示すものではない。

## 1. 使い方

Codexで `blanket11/imicue` の作業環境を開き、リポジトリ内の最新のdocsを読める状態にして、下の依頼文を渡す。URLだけではなく、読むファイル・今回の実装範囲・完了条件を指定する。

既存のAGENTS.mdがあれば、そのスコープに従って読む。docsはAGENTS.mdの代わりに自動的にすべて読み込まれると仮定せず、今回のプロンプトで明示する。AGENTS.mdの扱いは [公式資料 S11](08-references-and-decisions.md#s11) を参照する。

```text
docs/README.mdから案内されている仕様書01〜08を読んでください。
過去の会話を前提にせず、リポジトリ内の仕様を実装の基準にしてください。

今回の範囲は docs/06-implementation-and-tests.md の M0〜M2 だけです。
APIキー不要のローカルな最小版を、M0→M1→M2の順番で実装してください。

到達点は、架空の製品サイトに data-imicue-signal を付け、
利用者が明示的に計測を開始すると、閲覧・操作の集計と辞書の意味が確認でき、
ルールベースの判定結果をデモ画面で確認できることです。

辞書、観測事実、推定・判定、表示UIを分離してください。
辞書はsignalIdから内容の意味を説明するもので、購入意思を事実として加算しません。
ブラウザでは秘密キー・個人情報・入力テキストを収集しないでください。
同意撤回、長いsection、二重計測、古い判定応答、容量制限の仕様を省略しないでください。

実装前に短い作業計画を示し、そのまま実装とテストへ進んでください。
該当フェーズの受け入れ条件をテストにし、型検査・lint・unit test・
必要なブラウザ試験を実際に実行してください。
不足する細部は最小の合理的な案を採用して理由を記録し、
設計変更が必要なら仕様も更新してください。安全条件を黙って緩めないでください。

今回はJev実API、SaaS管理画面、課金、WordPressプラグイン、
npm公開、CDNへの公開、デプロイ、既存サイトへの導入は行わないでください。
Issue・GitHub Project・リポジトリ権限・LICENSEも変更しないでください。

未コミットの変更を保護し、作業ブランチで進めてください。
force pushや他人の変更の削除は行わず、自動マージもしないでください。

完了時に、変更内容、実行したテストと結果、未実施事項、
ローカルで試すための実際のコマンド、次の最小ステップを日本語で報告してください。
モックを実API確認済みと扱わず、未実装機能を完成済みと報告しないでください。
```

## 5. 実装時に特に守ること

公開APIの例は設計案であり、存在するパッケージをinstallして解決するものではない。内部型や関数名の細部は調整できるが、利用者との契約や安全条件が変わる場合はdocsとテストを更新する。

JevのquestionIdはアプリ側の応答対応用である。candidateIdをキーにするだけでモデルに対象が伝わると考えず、各質問に対象候補の意味を明示する。辞書のdescriptionから生成することで、同じ内容の手書き二重管理は避ける。

ライセンス変更、実サイトの利用データ、外部課金、公開・デプロイ、認証・権限などの判断は、実装上の細部として勝手に決めない。逆にテストファイルの配置等の低リスクな細部は、合理的に決めて根拠を残して進める。

M0〜M2はJevアカウント・キー・本番ユーザーデータなしで完了できる設計である。キーがないことをローカル版の実装停止理由にしない。

## 6. 仕様の更新と報告

実装後にREADMEへ使い方を書くときも、planned、implemented、testedを区別する。公式資料の変更を見つけたら、資料URLと確認日を08へ追記する。

docs/README.mdの初期状態記載は準備時点の記録なので、実装開始後は現在の状態に更新する。未実施試験を消して完成したように見せず、実装メモやPRの説明で残す。

機密を含まない差分と実行結果を、人がレビューできる単位で提示する。
