# 変更作業の進め方

開発者やコーディングエージェントが、このリポジトリへ変更を加えるためのガイド。Imicueの利用にエージェントは必須ではない。導入手順は[ドキュメント一覧](README.md)、コントリビューションの入口は[CONTRIBUTING.md](../CONTRIBUTING.md)を参照する。

## 変更前に現在の状態を確認する

作業ツリー、ブランチ、適用されるAGENTS.md、既存の差分を確認する。利用者の未コミット変更を保護し、関係する実装と[参照資料](README.md)を読む。過去の会話や古い実装記録だけで、現在のAPIや未実装範囲を判断しない。

変更の目的、対象ファイル、期待する動作、実行する検証を短く示す。ファイル配置などの通常の実装判断は既存の構成に合わせる。API契約・保存・課金・外部送信などに影響する変更は、影響を説明して依頼範囲を確認する。

## 守るべき境界

- 辞書、観測事実、判定、表示UIを分ける。閲覧を購入意思として記録しない。
- 秘密キーはサーバーだけに置き、ログ・Issue・コミット・スクリーンショットへ含めない。実ユーザーの入力や私的な運用情報を試験資料に使わない。
- 同意撤回、長い要素の計測、二重計測、古い判定応答、容量制限を維持する。変更するときは仕様とテストを同じ差分に含める。
- Jevへはコードで解決した辞書説明を渡す。候補IDだけで内容がモデルへ伝わるとは扱わない。
- 実APIの費用を伴う試験、デプロイ、npm公開、既存サイトへの導入は、依頼や運用方針で認められた範囲で行う。すでに認められた作業の許可を繰り返し求める必要はない。

Rules、モック接続、配布ビルド、通常テストにはJevのキーは不要。キーがない場合も、その範囲の作業と検証を進められる。

## レビューできる単位で変更する

作業ブランチで実装し、[テストと受け入れ条件](06-implementation-and-tests.md)の該当項目を検証する。mainへの反映はPull requestを使う。他者の変更の削除、force push、自動マージを通常の作業手順に含めない。

コミットメッセージの件名・本文は日本語で書く。Conventional Commitsの種別やコード識別子、製品名は原表記を保ってよい。設定値、認証情報、個人のメールアドレスやローカルの絶対パスが差分・生成物に混ざっていないかを確認する。

文書では実装済み・試験済み・未確認を分ける。利用者向けの見出しは「サーバーへ接続する」「配布ファイルを使う」のように目的で付ける。開発時のフェーズ名や会話中の依頼文を、導入の前提にしない。

## 完了時に報告する

変更によって利用者の動作がどう変わるかを先に説明する。実行したコマンドと結果、未実施の検証、その理由、ローカルで再現する手順を示す。モックを実APIの確認済みと扱わず、過去の試験を今回の結果として報告しない。

外部資料の前提が変わった場合は、確認日・出典・影響を[参考資料と設計判断](08-references-and-decisions.md)へ記録する。過去の数値や検証条件は日付付きの記録として保ち、現在の利用手順へリンクする。
